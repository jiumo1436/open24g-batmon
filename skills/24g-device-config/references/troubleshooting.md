# 读不到数？按现象查

先确认一件事：**校验器通过 ≠ 能读到数**。校验器只保证字段合法，
真正的判据是界面里「测试读取选中」有没有读出和厂商软件一致的百分比。

## 一次只改一个变量

读不到时最容易犯的错是「一口气改五处」。改得越多，越不知道是哪一处起的作用。
固定这个顺序，每步只动一处：

1. `match` 收到最小（只留 `vid`）→ 看能不能匹配到接口
2. `checksum` 全改 `none` → 排除校验算错
3. `query` 补上报告 ID、`pad_to` 改成实际长度 → 看有没有回包
4. `contains` 改短（2 字节）→ 看解析是否开始
5. `battery.byte` 逐个偏移试 → 找出接近厂商显示值的那个
6. 最后才加 `charging` / `range` / `zero_is_off`

## 现象对照表

| 现象 | 常见原因 | 处理 |
| --- | --- | --- |
| 完全匹配不到设备 | `vid` / `pid` 写错；设备在蓝牙模式 | 设备管理器核对硬件 ID；确认连的是 2.4G 接收器 |
| 匹配不到，但 VID 是对的 | `usage_page` 或长度条件太严 | 删掉 `usage_page` / `min_in`，先放宽再收窄 |
| 匹配到接口但一直没回包 | 漏了报告 ID；`pad_to` 长度不对；需要先握手 | `query` 首字节补报告 ID；`pad_to` = 整段长度；加 `pre` + `pre_delay_ms` |
| 有回包但解析不出电量 | `contains` 写错，或字节下标差 1 | 锚点必须逐字节一致；注意下标从锚点算起 |
| 偶尔读到、多数失败 | 帧发太快、设备休眠 | `listen_ms` 加到 900~1200，`attempts` 加到 2~3，加握手帧 |
| 读到但数值离谱 | 下标错、端序错、缺 scale | 先只写 `byte`，用厂商显示值反推比例 |
| 始终 0% | 关机假帧；或电量在别的字节 | 确认关机行为后开 `zero_is_off`；重新用差分法定位 |
| 数值跳变 | 回包里有两个相似字段（电量 / 续航分钟） | 对比放电曲线，选变化平滑的那个 |
| 充电时读到 100% | 有些固件充电时把电量字段写成 100 | 配合 `charging` 位显示，或用 `range` 挡掉 |
| 串口读不到 | 波特率错；端口被厂商软件占用 | 换 9600 / 115200 试；先关掉厂商软件 |
| 别人的电脑上读不到 | 配置里写死了 COM 号 / 端口 | `port` 留空 |

## 几个高频误区

- **「抓到帧了就等于适配好了」**：还要确认字节下标、换算、锚点都对得上真实电量。
- **「照抄别人的配置改改就行」**：不同固件版本的偏移经常不同，必须自己实测。
- **「为了提高匹配率把 match 清空」**：HID 至少要留 `vid`，否则会匹配到别人的设备。
- **「读到 0 就是没电」**：很多设备关机回 0，要 `zero_is_off` 区分。
- **「校验器过了就可以提 PR」**：没有实机验证证据的配置不会被合并。

## 数值对不上时怎么定位

拿两个不同电量的回包（厂商显示 87% 和 63% 时各抓一帧），跑：

```bash
python scripts/analyze_frames.py \
  --frame "06 A5 5A ..." --pct 87 \
  --frame "06 A5 5A ..." --pct 63
```

- 只有 1~2 个偏移跟着变 → 就是电量字段；
- 比例 `pct ≈ raw × 1` → 直接取用；
- 比例是 0.1 / 0.5 / 2 → 加 `scale`；
- 比例不稳定但单调 → 用 `map` 查表（抓 3~5 个点）。

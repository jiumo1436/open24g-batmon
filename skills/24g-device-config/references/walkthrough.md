# 一次完整的对话示例

下例演示交互节奏：问什么、怎么跑脚本、怎么交付。设备与数值均为虚构。

---

## 第 1 轮：用户开口

> 我有个示例品牌 K1 键盘，软件里没有，能加上吗

先要证据，一次问全，别挤牙膏：

```
能加。这台键盘的适配要三样东西，缺一样我先带你去拿：

1. VID / PID：设备管理器 → 找到这个接收器（拔插一次看哪项消失）→ 右键属性 →
   详细信息 → 属性选「硬件 ID」，把那行 HID\VID_xxxx&PID_xxxx&... 发我

2. 回包十六进制：软件右上角「捕获报文」→ 开始捕获，把文本框里的内容发我。
   或者用 Wireshark + USBPcap 抓一次。

3. 抓的时候厂商软件显示多少电？如果能再等它掉几个百分点抓第二帧，
   定位电量字节会准得多。
```

## 第 2 轮：用户把数据发过来

> 硬件 ID 是 HID\VID_2E4A&PID_1B2C&REV_0100&MI_02
> 抓包：查询帧 0A 5A A5 12 00 00 ...（20 字节）
> 回包 85% 时 0A 5A A5 12 00 00 00 00 55 00 00 00 00 00 00 00 00 00 00 66
> 回包 47% 时 0A 5A A5 12 00 00 00 00 2F 01 00 00 00 00 00 00 00 00 00 41

跑脚本（`--pct` 一定要带上，不然只能猜）：

```bash
python scripts/analyze_frames.py \
  --frame "0A 5A A5 12 00 00 00 00 55 00 00 00 00 00 00 00 00 00 00 66" --pct 85 \
  --frame "0A 5A A5 12 00 00 00 00 2F 01 00 00 00 00 00 00 00 00 00 41" --pct 47
```

关键几行：

```
[1] 所有帧等长：20 字节
    首字节恒为 0x0A：可能是 HID 报告 ID，也可能本身就是帧头。

[2] 共同前缀 8 字节：0A 5A A5 12 00 00 00 00
    A) contains = ["0A 5A"]  → 锚点从偏移 0 起
    B) contains = ["5A A5"]  → 锚点从偏移 1 起（把首字节当报告 ID）

[3] 偏移 8   1 字节 big    取值 85 / 47
            原始值 ≈ 百分比，直接取用；平均误差 0.0%
    A 锚点从 0 起 → "battery": { "byte": 8 }
    B 锚点从 1 起 → "battery": { "byte": 7 }

[4] [推荐] 末字节 = sum[1:19] & 0xFF
```

**判断锚点**：查询帧也是 `0A` 开头，说明 `0A` 是报告 ID 而不是帧头 → 选 B，
`contains` 用 `["5A A5"]`，`battery.byte` 用 7。

## 第 3 轮：交付

```json
{
  "format": "dianliang-device-pack",
  "version": 1,
  "devices": [
    {
      "key": "example-k1",
      "name": "示例品牌 K1 键盘",
      "type": "keyboard",
      "transport": { "type": "hid" },
      "match": { "vid": "0x2E4A", "pid": "0x1B2C", "usage_page": "0xFF00",
                 "min_in": 20, "min_out": 20 },
      "read": {
        "query": ["0A 5A A5 12 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00"],
        "checksum": { "mode": "sum_tail", "from": 1, "to": 19, "at": 19 },
        "pad_to": 20,
        "attempts": 2,
        "listen_ms": 800,
        "reply": {
          "contains": ["5A A5"],
          "battery": { "byte": 7 },
          "charging": { "byte": 8, "mask": "0x01" },
          "range": [1, 100]
        }
      }
    }
  ]
}
```

校验：`可用设备 1 台；错误 0 处`。

交付话术：

```
写好了：configs/devices/example-k1.json
- 20 字节定长报文，0A 是报告 ID（所以 query 带上了它）
- 电量在第 8 个字节（从锚点 5A A5 起算是第 7 位），直接就是百分比
- 末字节是 sum[1:19] & 0xFF 校验

实测三步：
1. 软件 →「＋ 导入设备」→「浏览 configs」→ 勾选 K1 → 导入
2. 右键卡片 →「测试读取」
3. 和厂商软件比，差 ±1~2% 算成功

现在还没在真机上跑过，读到数再告诉我；读不到我按现象表逐条排查。
另外：这台键盘关掉之后，接收器还会回包、电量写 0 吗？这决定要不要开 zero_is_off。
```

## 第 4 轮：用户回报读不到

> 导入进去了，点测试读取显示「未响应」

按**一次只改一个变量**处理，先放宽 `match`：

```
先把 match 里的 usage_page 和 min_in/min_out 去掉，只留 vid/pid 再试一次 ——
排除「条件太严导致接口没匹配上」。如果变成「匹配不到设备」，那就说明是长度或
usage_page 不对，我们回捕获报文里核对。
```

如果放宽后能匹配但仍无回包 → 下一步单独验 `checksum`：把 `"checksum"` 整段删掉
（等同 none）再测；仍不行才怀疑 `pad_to` 或报告 ID。

## 反面例子（不要这样做）

- 用户只给了一帧，就断言「电量在偏移 8」——单帧无法验证，只能算猜测
- 用户说「读不到」，一次性改 `match` + `checksum` + `contains` + `battery.byte`，
  然后说「再试试」——成功了也不知道为什么
- 校验器通过就说「已经适配好了」——校验器不碰硬件

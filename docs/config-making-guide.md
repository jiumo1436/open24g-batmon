# 配置制作教程：从抓包到一份能读数的 JSON

本文面向「手上有一台 2.4G 设备，但仓库里还没有它的配置」的用户。
按顺序做完，你会得到一份可以提 PR 的配置文件。

- 只想查字段含义？看 [字段说明](config-schema.md)。
- 已经写好配置，想提交？看 [贡献指南](contribute-guide.md)。
- 不想看原理，直接抄？从 [`configs/template.json`](../configs/template.json) 开始改，遇到问题回本文查。

> 全程只需要：一台 Windows 电脑、你要适配的那台设备、它的 2.4G 接收器、以及**厂商自己的驱动软件**。
> 厂商软件在这里的作用是「帮我们触发查询帧」，抓完就可以关掉。

---

## 1. 先理解我们要干什么

2.4G 无线外设（鼠标 / 键盘 / 耳机）的接收器插在 USB 口上，在系统里通常是一个 **HID 复合设备**：

```
接收器
├── 标准键盘接口      usage_page = 0x0001（系统自带的键盘功能）
├── 标准鼠标接口      usage_page = 0x0001（系统自带的鼠标功能）
├── 消费者控制接口    usage_page = 0x000C（多媒体键）
└── 厂商自定义接口    usage_page = 0xFF00 ~ 0xFFFF  ← 电量、DPI、灯光都走这里
```

厂商软件就是往「厂商自定义接口」写一段**查询帧**（Output Report），接收器再从
**Input Report** 回一段数据，电量就藏在这段回包的某个字节里。

我们要做的事，本质是三个问题：

1. **认接口**：这台接收器的厂商接口用哪个 `vid` / `pid` / `usage_page` / 报文长度？
2. **发对帧**：厂商软件发出去的那串十六进制是什么？要不要先握手？要不要校验？
3. **取对字节**：回包从第几个字节开始是电量？需要什么换算？

配置文件就是把这三个答案写成 JSON。程序只是忠实地照做。

## 2. 准备工作

### 2.1 查接收器的 VID / PID

1. 接收器插好，`Win + X` → 设备管理器；
2. 找到「人体学输入设备」里与接收器相关的项（通常带品牌名，或拔插一次看哪一项消失/出现）；
3. 右键 → 属性 → 详细信息 → 属性选「硬件 Id」，会看到：

```
HID\VID_1234&PID_1001&REV_0100&MI_02
        ^^^^     ^^^^
        VID      PID
```

`VID_1234` → 配置里写 `"vid": "0x1234"`；`PID_1001` → `"pid": "0x1001"`。
末尾的 `MI_02` 是复合设备的接口序号，说明这个接收器有多个接口 —— 我们要找的是厂商私有那个。

> 笔记本内置的蓝牙、触摸板也会出现在这里，别抓错对象。**只抓你自己的接收器。**

### 2.2 选抓包工具

| 工具 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- |
| **软件自带「捕获报文」** | 零安装，直接给出候选接口与报告 ID，还会主动发查询帧试探 | 只覆盖 HID 探测，不能长时间连续记录 | 第一次摸底、确认接口 |
| **Wireshark + USBPcap** | 完整 USB 报文流，可保存、可过滤、可对比 | 需要安装 USBPcap 驱动；个别机器抓不到 HID 中断传输 | 主力工具，推荐 |
| **Bus Hound** | 老牌，HID 抓取成功率高 | 界面古老，免费版有长度限制 | Wireshark 抓不到时的备选 |
| 硬件 USB 分析仪 | 最可靠 | 贵 | 一般不必要 |

先用软件自带功能摸底（第 3 节），再用 Wireshark 抓完整帧（第 4 节）。

---

## 3. 用软件自带功能摸底（最快）

1. 打开软件 → 右上角「捕获报文」；
2. 点「开始捕获」（约 1 秒）或「深度探测（约 20 秒）」；
3. 文本框里会列出本机每个厂商接口的 VID / PID / usage_page / 报文长度 / **描述符里的真实报告 ID**，
   以及按报告 ID 发试探帧后的回应。

这一步能直接回答「我的接收器有没有厂商接口、它多大、报告 ID 是几」。
如果连厂商接口都列不出来，说明这台设备的接收器没有暴露自定义 HID 接口（可能是纯串口方案，
见第 8 节），或者需要先装厂商驱动才能出现该接口。

---

## 4. 用 Wireshark 抓完整报文（主力方法）

### 4.1 安装

1. 安装 [Wireshark](https://www.wireshark.org/)，安装向导到「components」那一步**务必勾选 USBPcap**；
2. 装完重启（USBPcap 是内核过滤驱动）；
3. 打开 Wireshark，接口列表里应出现 `USBPcap1`、`USBPcap2`…（一个对应一个 USB 根集线器）。

> 接收器尽量插在**主板后置 USB 口**，不要经过外接 HUB / 扩展坞。
> 经过 HUB 时，部分机器的 USBPcap 抓不到 HID 的中断传输，包会是空的。

### 4.2 抓包

1. 双击 `USBPcap1`（不确定是哪个就逐个试，插拔接收器时哪个接口有数据流就是它）；
2. 在过滤栏输入（VID 换成 2.1 查到的值）：

   ```
   usb.idVendor == 0x1234
   ```

   只想看某个接口就再加 PID：`usb.idVendor == 0x1234 && usb.idProduct == 0x1001`；
3. 点开始捕获，然后**去操作厂商软件**，制造几次查询：
   - 打开厂商软件，等它刷新一次电量显示；
   - 在软件里切一下 DPI / 灯光 / 电量页面；
   - 把设备关机再开机（会有一批初始化帧，很有信息量）；
4. 抓到几百个包后停止。

### 4.3 在报文里找「查询帧 / 回包」

- `URB_INTERRUPT out`：主机 → 接收器，**这就是查询帧**；
- `URB_INTERRUPT in`：接收器 → 主机，**这是回包**；
- 展开某一帧，找 `HID Data`（Wireshark 4.x 字段名 `usbhid.data`，老版本是 `usb.capdata`）；
- 右键该字段 → Copy → …as Hex Dump，得到类似：

```
0000  06 a5 5a 01 00 00 00 00 00 00 00 00 00 00 00 00   ..Z.............
0010  00 9c                                             ..
```

**第一字节 `06` 是报告 ID**（描述符里定义的），后面的 `a5 5a 01 …` 才是厂商自己的协议。

> ⚠️ 本程序的引擎**按配置原样发送**，不会自动补报告 ID。
> 所以配置里的 `query` 要**把报告 ID 一起写进去**（照抄 HID Data 整段即可），
> `pad_to` 也按含报告 ID 的整段长度填。这是新手最容易错的地方。

### 4.4 判断哪一帧是「读电量」

| 线索 | 说明 |
| --- | --- |
| 周期性 | 厂商软件开着时每隔几秒出现一对 out/in，通常就是轮询电量 |
| 长度固定 | 同一对帧每次长度一致，只有个别字节变化 |
| 差分 | 抓两次（电量 A% 时、放电到 B% 时），逐字节对比，只有 1~2 个字节跟着变 → 那就是电量字段 |
| 对照显示值 | 厂商软件显示 87% 时，在回包里搜 `57`（87 的十六进制）；若两字节小端可能是 `57 00`，若 0.1% 精度可能是 `66 03`（870） |

对不上就换思路：有些设备电量是**电压**（如 `0F A0` = 4000mV），有些是**档位**（0~4），
需要用「查表」或「电压映射」换算，见 [字段说明 6.1](config-schema.md#61-电量换算-battery)。

### 4.5 判断校验方式

把一帧复制成十六进制，用下面这段脚本试三种常见校验（其余算法需自行推导）：

```python
frame = bytes.fromhex("06 a5 5a 01 00 00 00 00 00 00 00 00 00 00 00 00 00 00".replace(" ", ""))

def sum_tail(b, frm, to):      # 求和取低 8 位
    return sum(b[frm:to]) & 0xFF

def sum_neg(b, frm, to, seed): # (seed - 求和) & 0xFF
    return (seed - sum(b[frm:to])) & 0xFF

print("末字节 =", hex(frame[-1]))
print("sum_tail[1:17] =", hex(sum_tail(frame, 1, 17)))
print("sum_neg[1:17] seed=0x00 =", hex(sum_neg(frame, 1, 17, 0x00)))
```

哪个结果等于「校验位所在字节」，配置里就写哪种：

```json
"checksum": { "mode": "sum_tail", "from": 1, "to": 17, "at": 17 }
"checksum": { "mode": "sum_neg", "from": 1, "to": 17, "at": 17, "seed": "0x00" }
```

都不是？可能是 CRC16 / 异或 / 厂家自定义。先在配置里写 `"mode": "none"` 试试能不能读到数 ——
**很多接收器并不校验查询帧**，回包校验同理。读不到再回来研究校验。

## 5. 开始写配置

复制模板，改成你的文件名（小写英文 + 连字符）：

```bash
cp configs/template.json configs/my-brand-model.json
```

### 5.1 第一步：只填「能发出去」

```json
{
  "format": "dianliang-device-pack",
  "version": 1,
  "devices": [
    {
      "key": "brand-model",
      "name": "品牌 型号",
      "type": "mouse",
      "transport": { "type": "hid" },
      "match": {
        "vid": "0x1234",
        "pid": "0x1001",
        "usage_page": "0xFF00",
        "min_in": 18,
        "min_out": 18
      },
      "read": {
        "query": ["06 A5 5A 01 00 00 00 00 00 00 00 00 00 00 00 00 00 00"],
        "checksum": { "mode": "none" },
        "pad_to": 18,
        "attempts": 3,
        "listen_ms": 800,
        "reply": {
          "contains": ["A5 5A"],
          "battery": { "byte": 5 },
          "range": [1, 100]
        }
      }
    }
  ]
}
```

要点：

- `match` 里**不要同时写太多条件**：先 `vid` + `pid`，读到数后再补 `usage_page` / `min_in` 收窄；
  条件太多会「一台都匹配不上」；
- `min_in` / `min_out` 填**报文长度下限**，抓包里报文的实际字节数（含报告 ID）就是它；
- `contains` 填回包里稳定出现的一小段（帧头最佳，比如 `A5 5A`），太短（1 字节）容易误匹配，
  太长（含变化字节）会永远匹配不上；
- `battery.byte` 的**下标从锚点算起**：锚点占 2 字节时，帧头之后的第 3 个字节下标是 2。

### 5.2 第二步：用「测试读取选中」验证

1. 软件 →「＋ 导入设备」→「选择协议文件」→ 选你的 JSON；
2. 勾选这台设备 →「测试读取选中」；
3. 三种结果：

| 提示 | 含义 | 下一步 |
| --- | --- | --- |
| 读到电量 | 成功 | 补充电位、收紧 range、加 `wire` / `protocol` |
| 未响应 / 读不到 | 帧发出去了但没解析到 | 见第 6 节排查表 |
| 匹配不到设备 | `match` 条件没命中任何接口 | 用「捕获报文」看真实 usage_page / 长度 |

### 5.3 第三步：补细节

- **充电状态**：回包里表示「正在充电」的位，写成 `"charging": { "byte": 6, "mask": "0x01" }`；
- **关机假帧**：设备关机后回包仍在、但电量字段为 0 → 加 `"zero_is_off": true`，界面会显示
  「已关机」+ 上次读到的电量（并标注是几点读到的），既不会写死成 0%，也不会弹低电量提醒。
  **这个开关默认关闭，必须自己判断**：关机回的 0 和真的没电在协议层长得一模一样，程序不能替你猜
  （猜错的后果是把「真的没电了」显示成「只是关机了」）。判断方法：关掉设备看回包 —— 仍回包且电量
  字节为 0 就开；关机后接收器直接消失则根本读不到 0，开不开都一样；详见
  [configs/README](../configs/README.md#关机假帧zero_is_off-该不该开)；
- **range**：把明显不可能的值挡掉，例如 `[1, 100]`；如果设备真有 0%，就写 `[0, 100]` 并配合
  `zero_is_off` 区分「真 0%」和「关机」；
- **多帧查询**：有的设备要先发唤醒帧，写进 `pre`，并加 `pre_delay_ms`；
- **被动推送**：有的设备开机就主动推电量，`query` 可以留空，只写 `"passive_ms": 1500`。

## 6. 读不到？按这张表排查

| 现象 | 常见原因 | 处理 |
| --- | --- | --- |
| 完全匹配不到设备 | `vid` / `pid` 写错；设备在蓝牙模式 | 设备管理器核对硬件 ID；确认接收器（不是蓝牙）连着 |
| 匹配到接口但无回包 | 漏了报告 ID；`pad_to` 长度不对；需要握手 | `query` 首字节补报告 ID；`pad_to` 改成报文实际长度；加 `pre` 帧 |
| 有回包但解析失败 | `contains` 锚点写错 | 抓包复制回包前几个字节，注意锚点必须**逐字节一致** |
| 偶尔读到、多数失败 | 帧发太快 / 设备休眠 | 加大 `listen_ms`、`attempts`；加 `pre` 唤醒 + `pre_delay_ms` |
| 读到但数值离谱 | 字节下标错、端序错、缺 scale | 先写 `"battery": {"byte": n}` 原始值，用厂商软件显示值反推 |
| 一直是 0% | 关机假帧；或电量在别的字节 | 加 `zero_is_off`；用第 4.4 节差分法重新定位 |
| 数值跳变 | 回包里有两个相似字段（如「电量」与「续航分钟」） | 对比放电曲线，选变化平滑的那个 |
| 充电时读到 100% | 有些设备充电时电量字段被写成 100 | 加 `range` 上限或结合 `charging` 位显示 |
| 串口设备读不到 | 波特率错；端口被厂商软件占用 | 用串口助手按同一波特率验证；关掉厂商软件再试 |

调试建议：先用 `"mode": "none"` 的校验、最简单的 `battery`，把「能读到」跑通，再逐步加复杂度。
一次加五个字段，出问题就不知道是哪一个的错。

## 7. 高级换算速查

| 需求 | 写法 |
| --- | --- |
| 单字节直接是百分比 | `{ "byte": 5 }` |
| 两字节小端、0.1% 精度 | `{ "byte": 5, "bytes": 2, "order": "little", "scale": 0.1 }` |
| 取某几位 | `{ "byte": 5, "bytes": 2, "mask": "0x7F00", "shift": 8 }` |
| 取低半字节 | `{ "byte": 5, "mode": "lo" }` |
| 档位映射 | `{ "byte": 5, "map": [[0, 0], [1, 25], [2, 60], [3, 100]] }` |
| 电压 → 百分比 | `{ "byte": 3, "bytes": 2, "read_as": "voltage", "voltage_scale": 0.001, "voltage_min": 3.3, "voltage_max": 4.2 }` |
| 线性修正 | `{ "byte": 5, "scale": 0.98, "offset": 2 }` |
| 公式 | `{ "byte": 5, "formula": "min(100, max(0, x * 2 - 10))" }` |

优先级：`formula` > `map` > `read_as=voltage` > `scale`/`offset`。
公式是 AST 白名单求值，只能算数，不能执行代码 —— 配置来自陌生人也不怕。

## 8. 串口（虚拟 COM）接收器

有些设备的接收器不是 HID，而是一个虚拟串口：

1. 设备管理器 → 端口（COM 和 LPT）里看到 `USB-SERIAL CH340 (COM4)` 这类条目；
2. 用串口助手（SSCOM / PuTTY）以常见波特率（9600 / 115200）试发查询帧，确认能收到回包；
3. 配置里写：

```json
"transport": { "type": "serial", "port": "", "baud": 115200, "bytesize": 8,
               "parity": "N", "stopbits": "1" }
```

`port` **留空**：程序会用你在「设置 → 串口接收器」里手动选的端口，没选就逐个尝试本机串口。
写死 `"COM4"` 只在「这台设备必须独占某个固定口」时才用 —— 别人的电脑上未必是同一个号。

串口不需要 `match`（整个串口就是一个通道），`read` / `reply` 的写法和 HID 完全一样。

## 10. 常见误区

- **「抓到帧了就等于适配好了」**：还要确认字节下标、换算、锚点都对得上真实电量；
- **「直接用别人配置改改」**：不同固件版本的偏移经常不同，必须自己验证；
- **「为了提高匹配率把 match 全删了」**：`vid` 是必需的（HID），全删会把别人的设备也匹配进来；
- **「读数为 0 就是没电」**：很多设备关机回 0，必须用 `zero_is_off` 区分；
- **「配置写好就该进主库」**：没有实测证据的配置不会被合并，见 [贡献指南](contribute-guide.md)。

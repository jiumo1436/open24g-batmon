# configs —— 2.4G 设备协议配置库

这个目录就是项目的「设备支持列表」。**一份配置 = 一台（或多台）设备的协议描述**，
程序启动后由用户在这里导入，导入的记录写进用户自己的 `devices.json`。

源码里没有任何设备协议参数，所以：**这里有多少份经过验证的配置，项目就支持多少台设备。**

## 目录结构

```
configs/
├── devices/     # 实机配置：真实硬件上验证过，导入即用
└── templates/   # 模板与语法示例：供照抄着写，本身不对应可用设备
```

新增真实设备请放 `devices/`，写配置时参考 `templates/`。程序会递归扫描整个 `configs/`，
**只看文件名、不看层级**，所以放在哪一层都能被「浏览 configs」找到。

## devices —— 实机配置（种子设备）

下面四份是**真实硬件上验证过**的配置，可直接导入使用，也是「一份合格配置该长什么样」的参照：

| 文件 | 设备 | 协议特征 | 值得一看的地方 |
| --- | --- | --- | --- |
| `devices/vxe-r1-se-plus.json` | VXE R1 SE+ 鼠标 | 17 字节，取反校验 seed `0x4D` | `reply.checksum` 与发送帧用同一套种子；`range` 下限取 2 而非 0 |
| `devices/vgn-f1-pro.json` | VGN 蜻蜓 F1 Pro 鼠标 | 17 字节，与 VXE 同族但回包多一个报告 ID 前缀 | `reply.contains` 写成 `08 04` 两字节，锚点定在 0，`battery.byte` 随之为 6 |
| `devices/aula-f87.json` | 狼蛛 F87 键盘 | 20 字节，先握手再查询 | `passive_ms` 先听设备主动上报；`attempts` 特意设为 1，避免频繁唤醒 |
| `devices/xiberia-t7.json` | 西伯利亚 T7 耳机 | 64 字节，仅输出通道 | `min_in: 0` 表示输入无固定长度；`zero_is_off: true` 处理关机假帧 |

四台设备覆盖了目前最常见的四种形态：**单帧查询**、**握手 + 查询**、**大报文输出通道**，
以及**同厂协议变体**（帧结构相同、只是回包多一个报告 ID 前缀，锚点和字节下标要跟着挪）。
写新配置时可以先对照最接近的那一份改。

> VID / PID、Usage Page、报文长度都是产品级公开标识，同型号所有设备一致；这些配置里
> 不含 MAC 地址、序列号、抓包日志或任何本机路径。

## templates —— 模板与语法示例

| 文件 | 用途 | 会被「浏览 configs」列出吗 |
| --- | --- | --- |
| `templates/template.json` | HID 协议模板，逐字段带中文注释 | 否（文件名含 `template`，自动跳过） |
| `templates/serial-template.json` | 串口（虚拟 COM）协议模板 | 否（同上） |
| `templates/example-mouse.json` | 语法示例：单字节电量 + 取反校验 + 充电位 | 是 |
| `templates/example-keyboard.json` | 语法示例：握手帧 + 两字节小端 + 求和校验 | 是 |
| `templates/example-headphone.json` | 语法示例：串口 + 电压换算 + 关机假帧 | 是 |

> ⚠️ **三套 `example-*.json` 是纯虚构样例**：VID `0x1234`、帧头 `A5 5A` / `7E 01`、校验种子、
> 电量位置全部为编写语法而编造，**不对应任何真实产品，也不是任何人的私人调试配置**。
> 它们的作用只有两个：演示「一份能跑的配置长什么样」，以及在导入界面里点得动、看得懂。
> 拿真实设备去试，大概率匹配不到接口 —— 请按 [配置制作教程](../docs/config-making-guide.md) 自己写。

## 命名规范（提 PR 前必看）

- 全小写英文 + 连字符，禁止中文、空格、大写字母、下划线：
  `logitech-g304.json`、`razer-viper-v2-pro.yaml`、`vendor-xxx-2.4g.json`；
- 建议 `品牌-型号.json`，同一型号的不同固件版本可加后缀 `-fw2`；
- 文件名不要包含 `template`（会被批量导入当成模板跳过）；
- **一个文件放一台设备是推荐做法**，便于 review 和定位；同一系列多台设备也可合并，但要保证
  每台设备的 `name` / `key` 唯一。

## 一个文件里放多台设备

```json
{
  "format": "dianliang-device-pack",
  "version": 1,
  "devices": [
    { "name": "设备 A", "read": { "...": "..." } },
    { "name": "设备 B", "read": { "...": "..." } }
  ]
}
```

单台设备写错只会跳过那一台，不影响同文件里的其它设备（导入时会逐台给中文错误提示）。

## 关机假帧：`zero_is_off` 该不该开

这是写配置时最容易踩的坑，**几乎所有 2.4G 设备都会遇到**，先看清原理再决定。

设备关机后有三种表现，软件的对应行为完全不同：

| 关机时硬件怎么表现 | 软件看到什么 | 要不要配 `zero_is_off` | 卡片显示 |
| --- | --- | --- | --- |
| 接收器直接掉线 / 被拔掉 | 设备消失（`disconnected`） | 不用配 | 未连接 · 上次读数 X%（永久保留） |
| 接收器在，但整轮不回包 | 超时（`implnoread`） | 不用配 | 未响应 · 上次读数 X%（保留 30 分钟） |
| **接收器在、正常回包、电量字节写 0** | 读到 `0` | **要配 `true`** | 配了：已关机 · 上次读数 X%（永久）<br>不配：**直接显示 0%** |

关键点：**程序无法自己区分「关机假帧的 0」和「真的用到 0% 的 0」** —— 在协议层这两者完全一样。
猜错的代价很实际：把真实 0% 当成关机，用户会以为设备只是关了，其实已经彻底没电。
所以这个开关**默认关闭**，必须由了解设备实际脾气的人来声明。

判断方法：

1. 用「捕获报文」看设备**关机后**的回包 —— 仍在回包、电量字节为 `0`，就该配 `true`；
2. 关机后接收器直接消失、根本不回包，那永远读不到 0，配不配都一样；
3. 设备能一直工作到电量真正耗尽、并且你想看到那个 `0%` —— 保持 `false`（默认）。

```json
"battery": { "byte": 5, "zero_is_off": true }
```

> 另一种等效做法是把 `reply.range` 写成 `[1, 100]`：读到 0 会因越界被当作「没读到」。
> 效果相近但文案不同 —— 越界显示「未响应」，`zero_is_off` 显示「已关机」并永久保留上次读数。
> 想让用户一眼看出「这是关机了，不是掉线」，用 `zero_is_off` 更准确。

## 格式：JSON 还是 YAML

两者都支持，结构完全等价。**推荐 JSON**：不需要额外依赖，注释可用 `_` 开头的键代替。
用 YAML 需自行 `pip install pyyaml`（打包版已内置）。

## 提交前自检

```bash
python tools/validate-config.py                     # 校验本目录全部配置
python tools/validate-config.py configs/xxx.json    # 只校验一份
python tools/check-filenames.py                     # 文件名是否全为小写英文
```

`validate-config.py` 与程序内导入用的是**同一套校验逻辑**，通过它基本就能通过界面导入。

## 不接受的内容

以下内容会被直接关闭 PR，请勿提交：

- ❌ 私人抓包日志（`.pcap` / `.pcapng` / Wireshark 导出文本）、临时测试脚本、截图原图；
- ❌ 未在真实硬件上验证过的配置（「照抄别人的字段」不算验证）；
- ❌ 含 MAC 地址、序列号、个人路径、厂商账号信息的配置；
- ❌ 中文文件名、大写文件名、含空格的文件名；
- ❌ 修改 `app.py` 来「顺便支持」某台设备 —— 设备适配只能通过配置完成。

抓包日志与实测截图请在 PR 里以**附件/图片**形式提供（GitHub 评论上传），
不要提交进仓库 —— 仓库只保留可复用的配置本身。
